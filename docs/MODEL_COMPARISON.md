# 모델 비교 결과 기록 양식

아직 **측정하지 않은 표입니다.** 값을 채우기 전까지 발표에서 수치를 인용하지 마세요.

## 측정 방법

1. `npm run build && npm start`
2. `/lab` 에서 모드를 선택
3. `/capture` 에서 합성문서를 고르거나 인쇄본을 촬영
4. 분석이 끝나면 `/lab` → **마지막 분석 기록** 표에서 시도별 시간·모델·스키마 통과 여부를 읽음
5. GPU VRAM은 별도로 `nvidia-smi -l 1` 로 관찰
6. 아래 표에 옮겨 적음

각 모드 × 각 문서에 대해 **3회씩** 측정하고 중앙값을 적으세요. 1회 측정은 편차가 큽니다.

### 판정 기준

| 항목 | ✅ 조건 |
|---|---|
| 문서종류 정확 | `documentType`이 표의 문서와 일치 |
| 날짜 추출 | 원문의 기한이 `importantDates`에 정확히, 근거와 함께 |
| 금액 추출 | 원문 금액이 정확히. **KR-복지는 금액이 없는 것이 정답** — 값을 만들어내면 ❌ |
| 연락처 추출 | 문서 기재 번호와 일치. 없는 번호를 만들어내면 ❌ |
| Schema 통과 | 1차 시도에서 zod 검증 통과 (재시도 필요 시 ⚠️) |
| 근거 연결 | 모든 행동카드에 `evidenceIds`가 있고 실제 원문과 대응 |

### KR-복지 문서가 중요한 이유

이 문서에는 지원 금액이 적혀 있지 않습니다.
모델이 "보통 수십만 원" 같은 값을 만들어내면 **환각**이며, 이 표에서 ❌입니다.
`hardenAnalysis`가 근거 없는 금액을 `null`로 만들지만,
**모델 자체가 얼마나 자주 지어내는지**를 보는 것이 이 항목의 목적입니다.

## 관찰 메모

- 8B는 8GB VRAM에서 이미지 + 4096 토큰 문맥을 함께 올릴 때 시스템 RAM으로 넘어갈 수 있음.
  `nvidia-smi`의 VRAM이 상한에 붙고 응답이 급격히 느려지면 그 현상임.
- Ollama 첫 요청은 모델 로딩 때문에 느립니다. **워밍업 1회 후** 측정하세요.
- 일본어 세로쓰기·도장이 있는 실제 문서는 이 표의 합성문서보다 훨씬 어렵습니다.
  합성문서 결과를 실제 문서 성능으로 발표하지 마세요.
